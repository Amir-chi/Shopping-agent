# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

نزدیکا (Nazdika): a Persian, RTL, mobile-first assistant for in-person shopping in Tehran, backed by a Torob dataset snapshot (~226k products, ~332k offers, ~6.5k shops). One Django project (`nazdika/`) with one app (`catalog/`), PostgreSQL only, serving a framework-free vanilla-JS frontend. No build step, no npm dependencies.

Most docs (README.md, RUN.md, ARCHITECTURE.md, PRICE-SYNC.md, THEMES.md, OUTFITS.md, VIDEO-REVIEWS.md, …) are in Persian; ARCHITECTURE.md has the current feature-status table. `qa/` holds reference screenshots and test fixtures. **README.md and RUN.md partly describe older stages** (README: the static `app.js` prototype; RUN.md: the pre-Django SQLite `python server.py` server). The current runtime is Django/PostgreSQL via Docker; trust the code over those docs.

## Commands

```bash
cp .env.example .env            # then set DJANGO_SECRET_KEY (>=32 chars) and POSTGRES_PASSWORD
docker compose up --build       # app on http://127.0.0.1:${APP_PORT:-8000}
```

`docker/entrypoint.sh` runs `migrate`, then (unless `CATALOG_AUTO_IMPORT=false`) `import_catalog --if-empty` from `CATALOG_IMPORT_PATH` (default `/import/catalog.sqlite3`, a `.zip` also works; `./data` is mounted read-only at `/import`), then `collectstatic`. Settings refuse to load without a valid `DJANGO_SECRET_KEY`. `nazdika/env.py` loads `.env` for local `manage.py` runs; `.env` defaults `POSTGRES_HOST=db`, so running outside Docker needs `POSTGRES_HOST`/`POSTGRES_PORT` pointed at a reachable Postgres. A local `.venv` (Python 3.11) has the requirements installed; the Docker image uses Python 3.12.

Production runs on SSH host `hacaton_vps` in `/opt/nazdika` (no git there; code is copied as a tarball of the files the Dockerfile uses): `docker compose -f compose.yaml -f compose.prod.yaml up -d --build`. `compose.prod.yaml` adds Caddy (`deploy/Caddyfile`). Since 2026-10-23 it serves **plain HTTP on the bare IP `http://89.42.199.134`**, because the earlier `89-42-199-134.sslip.io` domain is DNS-filtered in Iran. On plain HTTP, browsers disable geolocation, the service worker and the clipboard, and the frontend falls back without them.

**HTTPS is https://sarrah.liara.run.** That address is the Liara PaaS app `sarrah`, a tiny Caddy proxy in `deploy/liara-proxy` that forwards to the IP:
- The app is in the user's Liara team «لیارا», so run `liara team use` first.
- Deploy it with `cd deploy/liara-proxy && liara deploy --app sarrah --platform docker --port 80`.
- It sends `X-Proxy-Key` (Liara env `PROXY_KEY`, equal to `LIARA_PROXY_KEY` in the server `.env`; compose refuses to start without it) and `X-Client-IP`.
- The server's `deploy/Caddyfile` trusts that visitor address and https only when the key matches. The pre-change Caddyfile, compose.prod.yaml and .env are in `/opt/nazdika-backups/https-20261023/` on the server. To bring HTTPS back with a real domain, restore a `{$SITE_DOMAIN}` site block, port 443 and `SITE_DOMAIN`, and switch `DJANGO_SECURE_COOKIES`/`DJANGO_CSRF_TRUSTED_ORIGINS` to https. Caddy keeps no access log, because query strings can carry location. The server `.env` differs from local: `DJANGO_DEBUG=false`, `DJANGO_TRUST_PROXY=true` (so rate limits use the first `X-Forwarded-For` hop, see `views.client_address`), and `DJANGO_ALLOWED_HOSTS` must keep `127.0.0.1` for the container healthcheck. Bump the `?v=` query strings in `index.html` on every frontend change. Production runs one gunicorn worker (`WEB_CONCURRENCY=1`, `GUNICORN_THREADS=4`) so the in-process cache and rate limits are shared. `gunicorn.conf.py` `when_ready` prewarms bootstrap, home and shop counts. `compose.prod.yaml` gives Postgres `shared_buffers=256MB`. Whole-catalog aggregates (bootstrap, per-shop product counts) go through `services.catalog_cached`, whose key changes whenever a Product, Shop or Offer is saved or deleted.

Management commands:
- `python manage.py import_catalog --sqlite data/catalog.sqlite3 [--if-empty]` (or `--zip <original.zip>` instead of `--sqlite`). Import is atomic and never replaces existing rows.
- `python manage.py sync_feed <file.json|csv> --shop-id shop_...` — ingest a merchant price/availability feed (contract in PRICE-SYNC.md).
- `python manage.py classify_categories` — assigns any leaf category missing from `catalog/taxonomy.json` to a department using the AI model. Run it after importing new data; existing mappings are kept.
- `python manage.py verify_catalog [--compare-source data/catalog.sqlite3]` — read-only acceptance checks (counts, aggregates, API responses) against the imported Postgres data; with `--compare-source` it digests every raw record against the SQLite source.

Tests:
- Django tests (current, seeded fixture, need Postgres): `python manage.py test catalog`; single test: `python manage.py test catalog.tests.test_api.CatalogTests.test_bootstrap_and_health`.
- Frontend checks are plain Node scripts (no deps) that load `catalog.js`/`shopping.js`/`reviews.js` into a `vm` context and render page functions: `node test_frontend.cjs`, `test_comparison.cjs`, `test_icons.cjs` (fixture `qa/redesign-icons.json`), `test_outfit_interview.cjs`, `test_ux_cleanup.cjs`, `test_video_reviews.cjs`, `test_offline.cjs` (runs `sw.js` against an in-memory Cache Storage). Only `test_frontend.cjs` needs a live server: it fetches real API responses from `API_BASE` (default `http://127.0.0.1:8000`, the Docker app's default port) with the full catalog imported. `node --check <file>.js` for syntax.
- Root `test_catalog.py` / `test_shopping.py` are **stale**: they call SQLite-era helpers (`server.prepare_features`, `server.Handler`, `server.connect`, `server.DB`) that no longer exist in `server.py`. The equivalents live in `catalog/tests/`.

## Architecture

**API**: apart from `/api/health` and the merchant feed, `nazdika/urls.py` sends every `GET /api/<anything>` to `catalog.views.api`, which calls `catalog.services.endpoint(path, args)`. That function is a hand-written regex router returning plain dicts (bootstrap, home, products, product stores/bundle, shops, shop products, outfits, video-reviews, assistant, compare-insight, market-fallback, price-status, offer history). New read endpoints go in `endpoint()`, not in `urls.py`. Views map `ValueError/KeyError/TypeError` to 400, `LookupError` to 404, and `DatabaseError` to 503. `server.py` and `price_sync.py` are compatibility shims that re-export `endpoint` and `catalog.prices.ingest`.

**Layers inside `catalog/`**:
- `domain.py`: pure logic with no ORM. Persian/Arabic digit normalization, query-constraint parsing (budget/installment inferred from free text), Tehran-time opening hours, haversine distance, garment slot/color classification and outfit scoring.
- `services.py`: ORM queries plus serialization into the frontend's JSON contract.
- `prices.py`: `ingest()` validates and applies merchant feed batches (shop-scoped, integer toman, timezone-aware timestamps, ≤500 offers, whole batch validated before writing).
- `models.py`: `Product`/`Shop`/`Offer` keep the original CSV row untouched in `raw` (JSON) and add only derived columns (`low`/`high`/`stores` aggregates, `search_text`/`search_document` FTS, `Garment`). Merchant updates go to `OfferState` (current) and `PriceEvent` (history). Snapshot prices are never overwritten.

**Departments**: the dataset's ~3,400 flat leaf categories are mapped to 17 departments (`catalog/taxonomy.py` GROUPS; re-classified 2026-10-23 with the Codex CLI from category names plus sample product titles; gold, coins, gemstones, jewelry and watches are `jewelry`, not `fashion`; sewing supplies are `home` + generated `catalog/taxonomy.json`). Listings that sellers misfiled under a wrong leaf (598 of them, such as a body gel under «کتاب چاپی») are moved per product by `catalog/product_departments.json`. Codex judged these from titles that share no common word with their own category. `taxonomy.in_department`/`department`/`moved_out` apply the moves to department filters, home rails, leaf pages and a product's `group`. `?group=` on `/api/products` filters by department.
- Search: when a search finds nothing, each unknown word is corrected to the closest word common in titles (`spelled`, from `ts_stat`, cached), and `parsed.corrected` reports it.
- Bundles: model-specific accessories (`FITTED`, such as cases and screen protectors) are offered only when their title names the product's `model`. `/api/home` (cached 30 min) returns departments and product rails.

**AI** (`catalog/ai.py`, `catalog/assistant.py`): BoxAPI chat completions, key only from `AI_API_KEY`. `/api/assistant` = router model (`AI_ROUTER_MODEL`, defaults to `AI_MODEL`; if it differs and the provider answers `model_not_allowed`, it retries with `AI_MODEL`) turns the question into filters → DB filtering → only a short candidate list goes to `AI_MODEL` (default `openai/gpt-6-luna`) for ranking. `/api/compare-insight` normalizes specs of 2–3 products. Model output is validated against known product ids, and prices or stock always come from the DB. Luna rejects non-default `temperature`, so `ai._post` never sends one. Both endpoints are rate-limited per IP in `views.api` and fall back to rule-based results when AI is unavailable. `catalog/outfits.py` builds outfits rule-first; `?review=1` adds an optional, bounded visual review by `AI_OUTFIT_MODEL` (separately rate-limited).

**Decor color advice** (`catalog/decor.py`, `decorPanel` in `shopping.js`): `POST /api/color-advice` (its own view in `urls.py`, not `endpoint()`) takes `{product_id, image}` for appliances-department products only. The image is a base64 data URL that the browser has already downscaled and re-encoded, which also drops EXIF/GPS. It is validated by magic bytes and size (≤700 KB), sent once to `AI_OUTFIT_MODEL` with `cache_seconds=0`, and never stored or logged. The model may only answer with colors from `PALETTE`. The product's own colors come from its color specs (`product_colors`, ignoring "رنگ نور"). In the dataset each listing usually has a single color, so a mismatch shows same-category listings in the recommended color, taken from the DB. `POST /api/photo-search` (`catalog/photo.py`, `#photo` page) uses the same photo checks and shared `views.photo_request` (with its own rate limit). The model only names the product type, brand and model it can see. `search_products` then tries `exact` → `keywords` → `brand` → `type` queries and reports which one matched. Nearest sellers are shown only for `exact`/`keywords` matches.

**Video reviews** (`catalog/video_reviews.py`, frontend `reviews.js`): `/api/video-reviews` searches YouTube via Supadata (`SUPADATA_API_KEY`, daily/monthly call caps, results cached in `VideoReviewCache`) for products in the mobile/digital/beauty groups, then summarizes only existing native captions (`VIDEO_REVIEW_SUMMARIES` toggles this). No downloads, no ASR, no model-invented sources. Search and summary are separate requests so links show up first.

**Buyer inquiries and seller panel** (`catalog/inquiries.py`, `catalog/seller.py`, `catalog/seller_views.py`, frontend `seller.js`). This is a working mock of buyer↔shop messaging: no SMS, call or push is sent. A buyer sends an inquiry from the contact dialog, or from the stores list to up to 5 shops (`POST /api/inquiries/new`). The buyer has no account: they keep a random token in localStorage, and the DB stores only its hash. They read their threads with `GET /api/inquiries?tokens=` (shown in the saved page) and reply with `POST /api/inquiries/reply`. Each inquiry is a thread of `InquiryMessage` rows; `seller_unread` drives the panel badges. The seller panel `#seller` logs in per shop with an access code from `manage.py seller_code <shop_id>`. The code and the session token are stored only as hashes, and a new code signs out old sessions. `SELLER_DEMO=true` (set on the server) adds a code-free demo login that can read and answer but gets 403 on price changes. Panel calls are `GET|POST /api/seller/<shop>/<overview|conversations|thread|products|reply|price>` with `Authorization: Bearer`; there is no public seller data under `/api/seller/`. `price` writes the shop's own observation through `prices.ingest` (valid for 24 h), the same path as the merchant feed. A reply in a thread goes only to that buyer and never changes public prices. Inquiries expire after 14 days. "Unmet demand" comes from `SearchMiss` (zero-result `/api/products` searches, normalized, phone-like text never stored, shown from 2 hits upward) and from inquiries other shops answered out of stock, both within the shop's categories. Frontend checks: `node test_seller.cjs`.

**Merchant feed**: `POST /api/merchant-feed/<shop_id>` takes Bearer auth against per-shop keys in the `NAZDIKA_FEED_KEYS` env JSON (each ≥32 chars). With no key configured the endpoint returns 503.

**Frontend**: `index.html` loads only `ui.css`, `catalog.js`, `shopping.js` and `reviews.js` (plus `market-guide.json` copied by the Dockerfile). Django serves them through a whitelist regex in `urls.py`, and assets through `/assets/...`. `catalog.js` holds global state, hash routing (`#home`, `#product?id=…`, `#stores`, `#outfits`, …), page render functions that return HTML strings, and the `esc()`/`image()` sanitizers. `shopping.js` adds outfits, market fallback and price-status pages on top of those globals. It extends pages by wrapping `views.*`, `loadRoute`, `readTarget` and `insightPanel` and splicing HTML into the result. That is how it adds the in-store price check (`/api/products/{id}/price-check`, one price per shop, compared with recorded prices only), today's web prices (`/api/products/{id}/web-prices` → `catalog/web_prices.py`: one Responses-API `web_search` call via `ai.web_search_json`, cached 6 h, rate-limited 10 per 10 min per IP; up to 3 distinct shops, each URL's host must be one the search saw and the price within 0.25×–4× of the recorded low; shown as unverified with links, never stored as a price; on request, or by itself when nothing is recorded; nothing found → "ask the seller"), the `#shared?ids=…` list link, the need-based comparison (`need` param → `for_need`), and the one-day route (`#route` from saved products → `/api/route-plan`; the planner is `domain.plan_route`, which uses straight-line legs and skips shops declared closed unless they are the only ones carrying an item). **«همین الان» is the main flow** (the hackathon brief asks for in-person decisions, not filters). Every home search goes to `#ask` (`askNow`), a minimal chat. Its answer comes from `/api/now?q&lat&lon[&at=HH:MM&day=mon…sun]` (`catalog/now.py`, rules only, no AI):
- The search results' dominant leaf categories define the item.
- Every shop within 12 km that records an offer in those categories, or lists the category in its profile, is checked against its declared hours at that moment: open, closed (with `domain.next_opening`: «۳۰ دقیقهٔ دیگر», «فردا ساعت ۱۰:۰۰»), or unknown.
- `kind` is `open_near` (open within 2 km), `open_far` or `none_open`.
- `hub` is the nearest roughly 1 km cell within 3 km where at least 4 such shops cluster. It is shown with the caveat that a shop there may be open without being listed.
- The frontend writes the decision as one bold sentence plus reasons, and shows one OpenStreetMap tile map: you, open/closed/unknown pins, and the area. A pin scrolls to its card.
- Cards offer route and «بپرس» (the inquiry flow, with the product).
- The demo time chips (الان / ۹:۳۰ شب / ۱۱:۳۰ شب / جمعه ۱۰ صبح / a custom time) set `at`/`day`.
- The old AI assistant stays at `#assistant`, linked from each answer.

It also adds «من این‌جام», a virtual location:
- `#locate` shows a Tehran map of OpenStreetMap zoom-12 tiles as plain `<img>` elements, with no map library. `spotAt`/`mapSpot` convert between a tap and lat/lon.
- `/api/nearby?lat&lon&ids=` (`services.nearby`) returns shops within 1.5 km in a straight line: up to 5 that carry products from «فهرست من», nearest first, otherwise the 3 nearest shops.
- The results become in-app notices: a toast, plus the «نزدیک تو» list on `#messages`, which counts toward the unread dot.
- Browser notifications are not used, because plain HTTP blocks them.
- The point lives only in localStorage (`state.virtualSpot`) and is sent as `precise`, so the service worker never caches those responses.

It also adds the dowry planner (`#dowry` → `/api/dowry`). Nothing on its checklist is pre-selected. Buyers may type up to 5 items of their own (`extra`); each maps to a category in the home, appliances, digital or lighting departments, preferring a category whose name contains the text. `DOWRY` in services.py maps checklist items to real leaf categories. The budget is split by each category's median recorded price (`split_budget`), and `tier_options` picks three listings near 0.65×, 1× and 1.4× each share. Tier labels follow price order. A call without `budget` returns only the checklist. Assistant extras live in `assistant.py`. Follow-ups send the last 3 turns as `history` (`history_of` sanitizes it). The router merges them, and "cheaper" caps `max_price` below the cheapest item already shown. The thread is kept in memory only, and `state.assistantFollowUp` stops a reload from re-asking a follow-up without its context. `/api/gift` (`#gift`) picks candidates by interest→department and price band, and the model only chooses among them. `/api/explain-specs` explains only the recorded specs, and gives a `fits_need` verdict only when a need is given. Both are rate-limited like the assistant. Shops carry `metro` (the nearest station within 2 km, straight-line) from `catalog/metro.json`, an OpenStreetMap snapshot (ODbL; the attribution is shown on the store page). There is no traffic-zone check yet, because no reliable boundary file exists. When you add a page function, add it to the route list in `test_frontend.cjs`, which renders every page and asserts no `undefined`/`NaN`. **Offline (PWA)**: `sw.js` (served at `/sw.js` for root scope) and `manifest.webmanifest`. Requests go to the network first and fall back to the cache: the app shell plus every same-origin `GET /api/*` already seen, capped at 300 entries. `api()` adds `X-Nazdika-Location: precise` when the origin came from device geolocation, and the worker never stores those responses. The page posts its versioned asset URLs to the worker, so the first visit is enough. The Claude desktop browser pane cannot register service workers, so test offline in a real Chromium. **Not loaded, kept for reference only:** `app.js`, `styles.css`, `catalog.css`. The Dockerfile copies only the live files, so a new frontend file must also be added there, in `urls.py`, and in `index.html` (cache-busting `?v=` query).

**Shopping extensions**: storefronts (`/api/shops/{id}/products` with category facets and the shop's own price), `bundle` (complementary categories per product, preferring one shop; `BUNDLES` in services.py), and outfits with slots top/bottom/shoes/outer/accessory (`GARMENTS` in domain.py; Garment rows rebuilt by migration 0002). Seller contact is a demo flow because dataset phone numbers are synthetic.

**Themes**: the app is branded «سرراه» in user-facing text, while code ids, localStorage keys and the repo still say nazdika. The default theme is `pop`, design C of the redesign canvas:
- White page with 2.5px black outlines and hard offset shadows (`4px 4px 0 #111`).
- Lalezar (`assets/lalezar-*.woff2`) for display type; Vazirmatn variable for body text.
- Colour blocks come from `--pop-hi`, `--pop-a`, `--pop-b`, `--pop-go` (the primary action) and `--pop-cream`. `pop` sets them to turquoise, coral, electric purple, yellow and light turquoise; `poplilac` («پاپ یاسی») to lilac, peach, deep teal, lime and light lilac; `popyellow` («پاپ زرد») to sunshine yellow, pink, royal blue, mint and warm cream. A bare `:root` rule gives the round-1 themes the yellow values for the shared pieces.

Its shape rules are the `[data-theme^="pop"]` block at the end of `ui.css`; the prefix match covers both pop palettes. The design C pieces every theme shares sit just above that block: colour tiles, the info strip, price stickers, shop tickets («کجا بخرم؟») and the ask card. The markup follows design C in all themes:
- Home: one line plus search with a photo button, four helper tiles, a strip of honest counts, the last product seen, then departments.
- Product: a photo card with a lowest-price sticker, spec chips, one ticket per shop with the best first, and a fixed bar with «موجوده؟ بپرس», compare and route.

The phone bar has 3 tabs: خانه، فهرست من (`#saved`, `listPage`), پیام‌ها (`#messages`). In-page links like `href="#specs"` scroll to that element instead of routing.

The other themes come from round 1, light with ink and orange: `ink`, plus `teal`, `olive` and `brown`, which share ink's tokens through one combined `:root[...]` rule and override only the accent. `night` is dark.

The choice is stored in localStorage key `nazdika-theme-v4` and applied by the allowlisting pre-paint script in `index.html`. The palette picker is the header `settings` button. A new theme id must be added in three places: `themes` in catalog.js, that allowlist, and the theme loops in `test_frontend.cjs`, which merge every `:root` rule naming the theme before checking contrast. Switching themes must not re-render pages or touch app state.

## Data-honesty rules (enforced by code and tests)

- Shop phone numbers and many shop names in the dataset are synthetic (`contacts_synthetic`, `name_synthetic`). Never present them as real.
- Prices below 1,000 or above 10 billion toman are treated as suspect (`usable_price`). The record stays but is excluded from price ranges and sorting.
- The installment filter counts only `payment_options.channel=in_person`. `unknown` is not counted as confirmed.
- `last_price_changed_at` is when the price last changed, not proof of stock. Merchant `observed_at`/`valid_until` are kept separately. Re-importing a feed must not refresh timestamps.
- User call reports live only in the user's browser (localStorage) and never become public prices. Precise user location is not persisted or logged. The gunicorn access log format deliberately omits query strings.
